## DB/schema

추가: `visits(id, scheduled_at, title, memo, created_at, updated_at)` 및 `scheduled_at` 인덱스.
제목 기본값은 `병원 진료`, 메모는 NULL 허용입니다. 시간은 UTC naive 저장, API는 UTC `Z` 응답,
화면과 날짜 범위는 Asia/Seoul 기준입니다.

기존 4개 테이블의 구조나 데이터에 대한 삭제·초기화·재작성은 없습니다. 기존 `create_all`로
누락 테이블만 생성합니다. 실행 중인 개인 앱의 서버에서 새 테이블이 생성된 상태도 확인했습니다.
개인 DB를 테스트 대상으로 사용하지 않았습니다. 개인 DB 파일은 schema 추가 때문에 바이트 해시가
달라질 수 있으며, 파일 자체가 변경되지 않았다고 주장하지 않습니다.

pytest는 `tmp_path` DB를 사용합니다. 브라우저 검증 서버는
`/private/tmp/honjatmal-v03-IbKSz5/browser.db`와 포트 8013을 사용했고 개인 서버 8000과 분리했습니다.
V0.2 테이블을 가상 데이터로 채워 V0.3를 시작하고 다시 시작해도 모든 기존 행이 동일한지 비교하는
데이터 보존 테스트가 통과했습니다.

## API

| 메서드 | 경로 | 결과 |
| --- | --- | --- |
| POST | `/api/visits` | 생성, 201 |
| GET | `/api/visits` | 전체/기간 조회 |
| GET | `/api/visits/{id}` | 단일 조회 |
| PATCH | `/api/visits/{id}` | 부분 수정 |
| DELETE | `/api/visits/{id}` | 삭제, 204 |
| GET (확장) | `/api/posts` | 선택적 기간 조회, 기존 최신순 유지 |

두 목록에 `start_date=YYYY-MM-DD&end_date=YYYY-MM-DD`를 사용할 수 있습니다.
시작일·종료일 모두 서울 날짜로 포함합니다. 같은 날짜를 양쪽에 전달하면 하루 조회입니다.
기간 미지정 시 전체, 한쪽만 전달하면 해당 방향만 제한합니다. 역전/잘못된 날짜는 422입니다.
Visit 예정 시각에는 timezone이 필수이며, 명시적 null/공백 제목도 거부합니다. 없는 id는 404입니다.
Post 기준은 `created_at`, Visit 기준은 `scheduled_at`입니다.

## 향후 구조와 현재 범위

Post를 복제하지 않고 실제 작성 시각을 사용합니다. Visit의 예정 시각과 생성/수정 시각을 분리하고,
MedicationLog의 예정 날짜/예정 시각/실제 복용 시각을 유지합니다. 향후 직전 Visit과 대상 Visit 사이의
Post 및 MedicationLog를 동일한 UTC 구간으로 조회할 수 있습니다. 구체적 경계 규칙은 README에 기재했습니다.

AI/LLM 호출, 요약, 알림은 구현하지 않았습니다. 현재 달력은 전체 Post/Visit을 받아 집계하며,
대규모 데이터의 월별 로딩 최적화는 추후 기간 API로 전환할 수 있습니다.
